# ADR-0001: Benchmark results are stored in a separate repository

Status: Accepted · Date: 2026-10-04

## Context

The bench produces raw per-frame results (`result.json`, roughly 50-150 KB each), logs and segmentation spot-check images for every
engine, configuration, repetition and phase. Committed to this repository they would grow its history permanently: a deleted file
still lives in every clone.

The tables in this repository are only worth something if each number can be traced back to the raw data it came from and checked.
Accuracy numbers can be regenerated from the code commit, because synthetic frames and runners are deterministic. **Timing numbers
cannot**: they depend on the machine and the moment, so losing their raw data loses them for good.

Options considered:

1. **Commit results here.** Simple, but the history grows with every published run.
2. **GitHub Release assets of this repository.** Outside git history and easy to download. Immutable releases
   ([GitHub, October 2025](https://github.blog/changelog/2025-10-28-immutable-releases-are-now-generally-available/)) lock assets
   and the tag against modification, but the **whole release can still be deleted**, after which the tag can be deleted too (its
   name cannot be reused). They protect against tampering, not against loss.
3. **A versioned npm package** (the route `webarkit/webarkit` reserves for test media). Built for media that rarely changes, awkward
   for results that are added at every phase.
4. **A separate results repository.** Git history is the record; a deleted archive stays recoverable from earlier commits, and a
   ruleset can forbid force pushes and branch deletion.

## Decision

* Raw results live in a separate repository, **`webarkit/artoolkit-nft-bench-results`**, the primary and authoritative store. It
  always has the **same visibility as this repository**: both start private, and they are made public together. Visibility is
  therefore not part of this decision, and changing it does not require a new ADR.
  It is append-only: one commit per publication, never rewritten. Its default branch is protected by a ruleset that forbids force
  push and deletion.
* This repository keeps only code, marker datasets, the small test clip, the markdown tables, and **`results/manifest.json`**: one
  entry per publication with archive name, SHA-256, size, the code commit that produced it, the results-repo commit that stores it,
  and the release tag if one exists.
* Optionally, the same archive is also attached to an **immutable** release `results/<name>` of this repository, as a convenient
  download and a tamper-evidence check. The manifest records it, but it is never the only copy.
* During development, results stay in `results/local/` (git-ignored). Nothing is published per commit; publication happens when a
  result supports a written conclusion (normally the end of a phase), through `scripts/publish_results.sh <name>`, which archives,
  hashes, commits to the results repository, optionally uploads the release asset, and updates the manifest.
* **No data identifying people or machines is published.** Result headers contain only allow-listed fields (`host_label` chosen
  by us, OS, CPU model and core count, RAM, compiler/runtime and flags, code and engine versions); host names, user names, emails,
  absolute paths, environment variables, tokens, IP/MAC addresses and device serials are forbidden. The publish script scrubs logs
  (absolute paths become `<repo>`-relative) and refuses to publish if any forbidden pattern remains, naming the file and line. The
  full list is in `AGENTS.md` and `CONTRIBUTING.md`.
* The scorer verifies the SHA-256 against the manifest before scoring a downloaded archive.
* Decoded frame banks are never stored anywhere; they are regenerated by a command.

## Consequences

* The code repository stays small regardless of how many runs are published.
* Every published number is traceable to an archive whose integrity is checkable, held in a store whose history cannot be silently
  rewritten.
* Two repositories must be kept in step; the manifest is the link, and the publish script is the only supported way to write it.
* Access to raw results follows access to the code: whoever can read this repository can read the results repository.
* A mistaken result is never deleted: a new publication supersedes it and the manifest records the supersession.

## To revisit

* If the results repository grows past a few GB, split archives per phase into separate repositories or move to dedicated storage.
* Before both repositories are made public, check that no raw result exposes host details that should stay private (machine
  names, user paths in logs). This is a checklist item, not a change to the decision.
* 2026-10-04: on the organisation's current plan, GitHub refuses both rulesets and classic branch protection on private
  repositories (HTTP 403, "Upgrade to GitHub Pro or make this repository public"). Until the repositories are public or the plan
  changes, the "no force push / no deletion" guarantee is not enforced by GitHub; it holds by convention, and every archive stays
  verifiable through its SHA-256 in `results/manifest.json`. Enable the ruleset as soon as it becomes available.
